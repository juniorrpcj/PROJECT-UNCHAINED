# Security Policy

## Project Unchained

### 1. Purpose

Project Unchained takes cybersecurity, privacy, and the protection of contributor information seriously.

This document establishes the procedures for reporting security vulnerabilities and handling potential security incidents affecting project repositories, infrastructure, applications, or services.

We encourage responsible security research that helps improve the safety and reliability of open-source technology.

### 2. Supported Versions

Security updates are prioritized for actively maintained versions of Project Unchained software and infrastructure.

| Version | Security Support |
|---|---|
| Latest stable release | Supported |
| Previous releases | Evaluated individually |
| Development branches | Best effort |
| Archived projects | No guaranteed support |

Specific support arrangements may be established for individual repositories.

### 3. Reporting a Vulnerability

**Please do not publish sensitive vulnerability details in public GitHub Issues or Pull Requests.**

Security vulnerabilities should be reported privately.

Preferred reporting methods:

1. GitHub Private Vulnerability Reporting, when enabled.
2. The repository's designated security contact.
3. Another private communication channel officially established by the maintainers.

### 4. Information to Include

When reporting a vulnerability, please provide:

- A clear description of the issue.
- The affected repository, application, or component.
- The affected version or configuration.
- Potential security impact.
- Reproduction steps, if safe and authorized.
- Supporting evidence or logs, with sensitive information removed.
- Suggested mitigation, if available.

Reports should contain enough information to allow maintainers to understand and assess the issue.

### 5. Responsible Disclosure Principles

Security researchers participating in Project Unchained activities must:

- Obtain authorization before testing systems.
- Avoid accessing or exposing third-party data.
- Avoid disrupting services or infrastructure.
- Avoid destructive testing.
- Protect confidential information.
- Coordinate disclosure with affected maintainers.
- Comply with applicable laws and regulations.

Unauthorized testing is not permitted merely because a system is publicly accessible.

### 6. Vulnerability Handling Process

After receiving a report, maintainers will make reasonable efforts to:

1. Acknowledge receipt.
2. Assess the reported vulnerability.
3. Determine affected components and severity.
4. Coordinate remediation.
5. Prepare appropriate security updates.
6. Coordinate public disclosure when appropriate.

A response acknowledgment target of seven calendar days is recommended, although complex incidents may require additional time.

### 7. Severity Assessment

Vulnerabilities may be classified using the Common Vulnerability Scoring System (CVSS), where applicable.

| Severity | General Description |
|---|---|
| Critical | Severe compromise or widespread impact |
| High | Significant security exposure |
| Medium | Limited but meaningful security risk |
| Low | Minor security weakness |
| Informational | Security observation without demonstrated impact |

Severity assessments may change as additional evidence becomes available.

### 8. Public Disclosure

Vulnerability details should not be published prematurely when doing so could expose users or infrastructure to unnecessary risk.

Maintainers and reporters should coordinate disclosure whenever reasonably possible.

Public advisories should provide:

- A description of the issue.
- Affected components and versions.
- Security impact.
- Available mitigations or fixes.
- Relevant acknowledgments.

### 9. Security Researcher Recognition

With the researcher's permission, Project Unchained may acknowledge responsible security contributions in security advisories or project documentation.

Recognition does not constitute employment, financial compensation, certification, or legal immunity.

### 10. Data Protection

Security reports must not include unnecessary personal data, credentials, private keys, access tokens, or confidential third-party information.

Any sensitive information accidentally received must be handled with appropriate care.

### 11. Security Incidents

Suspected compromises involving project infrastructure, repository permissions, credentials, or confidential information should be reported immediately through an appropriate private channel.

Maintainers may temporarily restrict access or suspend affected services while investigating.

### 12. Limitations

Project Unchained does not provide blanket authorization to test third-party systems, networks, applications, or services.

Any authorized testing must have clearly defined scope and written permission from the relevant system owner.
